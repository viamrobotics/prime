# @viamrobotics/prime-ui

Viam's Svelte 5 component library, the v2 of prime. Components wrap well-maintained **headless** primitives ([bits-ui](https://bits-ui.com)) or native elements, dressed in `@viamrobotics/tailwind-config` design tokens. Source lives in `src/lib/`. There is no app in this package: the docs site ([docs](../../docs/)) is where components are demonstrated and where you look at them while developing.

## Layout

- `src/lib/`: published source. Add components here. `src/lib/index.ts` re-exports the public API.
- `dist/`: generated by `svelte-package` during `pnpm build`. It is what npm sees via the `files` field.

## Stack

| Layer         | Tool                                                                    |
| ------------- | ----------------------------------------------------------------------- |
| Framework     | Svelte 5 (runes). `svelte-package` builds `dist`, with no app framework |
| Headless base | [bits-ui](https://bits-ui.com) (styled) + native elements               |
| Bundler       | Vite                                                                    |
| Styles        | Tailwind CSS v4 + `@viamrobotics/tailwind-config` tokens                |
| Tests         | Vitest (browser mode for `.svelte`)                                     |
| Typecheck     | `svelte-check`                                                          |
| Lint/format   | ESLint (+ `eslint-plugin-perfectionist`) + Prettier                     |

## Workspace deps

`@viamrobotics/tailwind-config` is a regular `dependencies` entry at `workspace:^`, which pnpm rewrites to a concrete caret range at publish time. It is not a peer dependency on purpose: changesets bumps a package to major whenever one of its peers gets a minor bump, so a token addition in tailwind-config would major every component package. A consumer that also installs tailwind-config directly dedupes to one copy while the ranges overlap, and a second copy of a tokens-only stylesheet redefines the same custom properties to the same values.

`@internationalized/date` is a bits-ui peer dependency. Nothing in `src/lib` imports it, but it stays in `dependencies` so bits-ui resolves it without every consumer installing it by hand.

## Commands

Run from the repo root with a `--filter`, or from inside this package:

```bash
pnpm --filter @viamrobotics/prime-docs dev        # the component dev loop: docs site, hot-reloading this package's source
pnpm --filter @viamrobotics/prime-ui build        # svelte-package + publint
pnpm --filter @viamrobotics/prime-ui check        # svelte-check
pnpm --filter @viamrobotics/prime-ui test         # vitest, one shot
pnpm --filter @viamrobotics/prime-ui test:unit    # vitest, watch mode
pnpm --filter @viamrobotics/prime-ui lint         # prettier --check + eslint
pnpm --filter @viamrobotics/prime-ui format       # prettier --write
```

Root scripts (`pnpm build`, `pnpm check`, `pnpm lint`, `pnpm test`) fan these across the workspace.

`build`/`check`/`lint`/`test` (and the internal `package` step) are orchestrated by [wireit](https://github.com/google/wireit): each declares its inputs/outputs so unchanged work is skipped or restored from cache, locally and in CI. To force a real re-run, prefix with `WIREIT_CACHE=none`.

## Where components are demonstrated

The docs site is the only consumer of demos. Every component has a page under `docs/src/content/docs/packages/prime-ui/components/<slug>.mdx`, with its `Sandbox` demo and states showcase beside it in `<slug>/`. **A new component is not done until it has a docs page.**

`astro dev` aliases `@viamrobotics/prime-ui` to `src/lib/index.ts`, so edits here hot-reload into the docs with no build. `astro build` uses the package's `svelte` export (`dist`), so the published site renders what npm consumers get. The alias lives in `docs/astro.config.mjs`.

## Authoring components

Follow [.claude/rules/svelte.md](../../.claude/rules/svelte.md): runes only, a typed `Props`, `$props()` with a rest spread, `$derived` for computed classes and never `$effect`, `{@render children?.()}`, and array or object class syntax.

### Public API: never leak the headless library

The public surface stays in **native / web-standard vocabulary**. Never surface a bits-ui prop or callback name (`onCheckedChange`, `onValueChange`, …): a consumer shouldn't need to learn bits-ui, and swapping the headless lib must not break the API. Extend the matching `svelte/elements` attribute type and `Omit` what you re-type or drop, e.g. `interface Props extends Omit<HTMLButtonAttributes, 'value'>`. This applies to every part of a compound too: never type a part's props as `Select.TriggerProps` or another bits-ui export. bits-ui requires `id` to be a string and floating content's `dir` to be `ltr` or `rtl`, so a part that spreads onto a bits-ui element narrows those two fields in its `Props` with a one-line doc saying why.

### One `class`, one root, decoration is a snippet

A component is atomic: `class` lands on its root element and that is the only class prop. Never add a second class prop for an inner element (`inputClass`, `iconClass`, …). An internal decoration the consumer may want to resize, recolor, or replace (a checkbox or radio icon, a trigger chevron, a required asterisk) is an optional snippet prop with the default rendered in its `{:else}`: `indicator?: Snippet<[{ checked: boolean }]>` on `RadioGroup.Item`, `indicator?: Snippet` on `Select.Trigger` and `Label`, `children` on `Checkbox` since it has nothing else inside. Render the default inline in the `{:else}` branch. Do not declare a `{#snippet}` inside an `{#if}` to pass it to a bits-ui component: a snippet is only a prop of the component when it is a direct child of its tag, anywhere else it is a local declaration nothing renders, with untyped parameters.

### State & binding

Value/selection props are `$bindable`. Consumers manage state with **standard Svelte 5 bindings, not change callbacks**. Two supported modes:

- **Two-way**: `bind:checked` / `bind:value`. The default.
- **Fully controlled**: a `bind:` _function binding_, `bind:value={() => v, (next) => { … }}`. The setter is the source of truth, so it can transform or **veto** (no write means no change) and runs on every user-initiated change. To merely react, including to programmatic changes, use `$effect`.

Two component flavors:

- **bits-ui widgets (`Checkbox`, `Switch`, `RadioGroup`, `ToggleButtons`, `Select`, `Collapsible`, `Tabs`, `Menu.CheckboxItem`, `Menu.RadioGroup`) are BIND-ONLY**, with no change-callback prop. Declare the prop with **no fallback** (`let { checked = $bindable() } = $props()`) and bridge to the bits-ui child with a function binding that supplies the fallback (`bind:checked={() => checked ?? false, (next) => (checked = next)}`). A `$bindable(false)` fallback throws Svelte's `props_invalid_value` when a consumer binds state that starts `undefined`, and bits-ui's own `Checkbox` and `RadioGroup` carry fallbacks too, so `undefined` must never reach them through `bind:`. No synthesized DOM-event callbacks: a widget fires no `change` or `input`, so nothing fabricates one.
- **native inputs (`Input`, `NumberInput`, `Textarea`) keep native handlers**: each renders one real `<input bind:value>` (or `<textarea>`) with no wrapper, so `oninput`/`onchange`/`onblur`/… pass through via `{...restProps}` for side effects, alongside `bind:value`. `Input.value` is a `string`, and its `type` admits only the native types whose value is a string (`number`, `range`, `checkbox`, `radio`, and `file` are excluded, since Svelte binds them differently). `NumberInput` renders its own `<input type="number">` with `value?: number` and a `step` that admits the native `'any'`. A specialized input component is warranted only when the value type differs (`NumberInput`) or native UI is missing (date and time fields, pin input). Otherwise it is `Input` with a `type`, never a `TextInput` or `PasswordInput` beside it. `Textarea` is the multi-line one, growing with its content through `field-sizing: content` with `rows` as the fallback. An empty `NumberInput` is `undefined`; a string-valued control starts `undefined` and binds `''` once the user has cleared it, which is what Svelte's `bind:value` yields there. All three take their Field wiring from `Input/useInputControl.svelte.ts` so they never drift, and all three wear the `input` class from `@viamrobotics/tailwind-config`, which reads `disabled`, `readonly`, `aria-invalid`, and `data-field-state` off the element. Adornments (a leading icon, a unit suffix, `Field.StateIcon`) go in an `Input.Group` (`Input/InputGroup.svelte`): it wears the same `input` class, whose `& > input` rule strips the inner input's border, padding, and background and whose `:has(> input…)` alternatives restyle the group from the input's attributes, so no context and no JavaScript are involved. It forwards a pointer-down on its padding to the input. No `!important` anywhere: precedence is expressed in the selectors.
- **widgets still forward DOM handlers.** `Checkbox`, `RadioGroup.Item`, and `Select.Trigger` render a real `<button>`, and bits-ui composes a consumer `onfocus`/`onblur`/`onclick`/`onkeydown` with its own (consumer first, `preventDefault` stops bits-ui's). What never fires is `change`/`input`, since no native control changes: that is the reason for bind-only, not a lack of pass-through. `focus`/`blur` do not bubble, so a group-level listener on `RadioGroup` is `onfocusin`/`onfocusout`. `Select` renders no element: its `Props` is a plain interface with no HTML attributes, so a handler or `class` on `<Select>` is a type error instead of a silent drop. They belong on `Select.Trigger`.

Full model, including the two edge cases (Svelte cannot detect if a prop is bound, and native `bind:value` reads the input's runtime `type`) live in [docs/src/content/docs/packages/prime-ui/components/state.mdx](../../docs/src/content/docs/packages/prime-ui/components/state.mdx).

### Field: form parts expect to live in one

`Field` (`Field/Field.svelte`) is the form-field wrapper and the state manager for everything inside it. It provides a context (`Field/useField.svelte.ts`: `provideField` / `useField`) carrying `controlId` (the id it assigns to the control, from `$props.id()` unless the `controlId` prop is given, while a plain `id` lands on the wrapper div like any attribute), `disabled`, `required`, `state` (a `FieldState` from `Field/state.ts`: `none`, `info`, `warn`, `error`, with the `fieldState.is*` type guards beside it for a narrowed check), and two registries: labels (for `aria-labelledby`) and hints (for `aria-describedby`). Every form part reads it:

- `Label` → `for`, `required`, `disabled`, and registers its id.
- `Hint` → `disabled`, `state` (`error`, `warn`, and `info` each color the text), and registers its id.
- `Field.StateIcon` (`Field/StateIcon.svelte`, the compound part) → `state`, rendering the matching icon or nothing. It takes a `state` prop standalone. Place it where the layout wants it, usually inside an `Input.Group`.
- `Input` / `NumberInput` / `Textarea` / `Checkbox` / `Switch` / `RadioGroup` / `ToggleButtons` / `Select` / `MultiSelect` + `Select.Trigger` → `id`, `disabled`, `required`, `state`, `aria-describedby`, and `aria-labelledby` on `RadioGroup` and `ToggleButtons` (a `role="radiogroup"` or `role="group"` div is not labelable by `for`). Every control sets `aria-invalid` on `error`: the inputs and `Select.Trigger` turn their border through the shared `input` class, which keys on `aria-invalid` and `data-field-state`, the checkbox and radio indicators turn `text-danger-dark` (radio items through `group-aria-invalid:` off the group root).

Rules when adding or changing a form part:

- **A prop passed directly always wins.** Declare the prop with no default (`disabled`, not `disabled = false`) and resolve `prop ?? field?.value ?? fallback` in a `$derived`. Svelte cannot tell "absent" from "undefined", so a default would shadow the field.
- **`useField()` returns `undefined` outside a `Field`.** Parts keep working standalone with explicit `id` / `for` / `aria-describedby`. Make it throw instead only as a deliberate decision.
- **Register from an `$effect`** (`$effect(() => field?.describe(id))`, the return value unregisters). The registry writes untracked so the effect does not depend on the list it appends to. Registration runs client-side only, so SSR output lacks `aria-describedby` until hydration.
- `Field` renders a bare `<div {...restProps}>` with no layout classes. Consumers pass `class`.

### Exports: single vs compound

`src/lib/index.ts` is the public API.

- **Single-part** → default-export directly: `export { default as Checkbox } from './Checkbox/Checkbox.svelte'`.
- **Multi-part** → a **compound** value in `<Folder>/<name>.ts`: `Object.assign` the parts onto the root with an **explicit `typeof` annotation**, then `export { Name }` from index:
  ```ts
  // Field/field.ts
  import Root from './Field.svelte';
  import StateIcon from './StateIcon.svelte';
  export const Field: typeof Root & { StateIcon: typeof StateIcon } = Object.assign(Root, {
  	StateIcon
  });
  ```
  This gives both `<Field>` and `<Field.StateIcon>`. The annotation is **required**: a bare `Object.assign` (or object literal) makes `svelte-package` inline the inferred type, hit each component's un-exported `Props`, and fail d.ts emit with _"cannot be named"_. The `typeof` query defers it. Keep the barrel minimal, with no helpers, maps, or state modules. The docs loader parses the barrel: each part must be imported as `import Part from './Part.svelte'` from the **same folder**, and listed in the `Object.assign` object as shorthand. A compound that loses its `Object.assign` is silently dropped from the docs, so repoint `index.ts` at the `.svelte` file when a component goes single-part.

A root that owns data its parts render shares it through a context module beside the barrel, the way `Select` shares `items` through `Select/useSelect.svelte.ts` so `Select.Items` can render one `Select.Item` per entry. `items` is the single source of truth there: bits-ui reads it for the closed trigger's label and for typeahead while the list is closed (arrow keys on a closed trigger open the list), so it can never be dropped in favor of the rendered children.

### ToggleButtons and Tabs

`ToggleButtons` is bits-ui's single-select `ToggleGroup`, which renders the items as `role="radio"` with `aria-checked` inside a `role="group"` and no `aria-pressed`. One option is always selected: the bridge's setter ignores bits-ui's empty write when the selected item is clicked again. `ToggleButtons.Item` carries its own fused-row styling keyed on `data-state="on"` rather than the `button` class, whose `:hover` rule outranks a utility on the same element.

`Tabs` is compositional like every other compound: `Tabs.List` holds one `Tabs.Trigger` per tab and `Tabs.Content` is the panel. Each trigger registers its `value` with the root context (`Tabs/useTabs.svelte.ts`) in mount order, so a selection whose tab is gone falls back to the first remaining tab inside the component. A strip with one tab is the consumer's `{#if}` around `Tabs.List`. Each trigger renders through bits-ui's `child` snippet as a `<div role="tab">` so a control inside it (a close `icon-button`) is valid HTML; the same wrapper drops bits-ui's `type="button"` and lets a key event from a nested control pass bits-ui's handler, which would otherwise swallow Enter and Space. A nested control stops click propagation itself so the click does not select the tab.

### Icon

`Icon` takes an `icon` prop: an SVG path string (an `@mdi/js` export, drawn on a 24×24 viewBox) **or** any Svelte icon component, rendered directly. prime ships no icon set: mdi is what the Viam app renders, so consumers bring `@mdi/js`, and internal parts import the few paths they use (`mdiChevronDown`, `mdiCheck`, …) rather than a shared map. The hand-drawn Viam glyphs live in `src/lib/Icon/icons/` as components over an internal `Glyph.svelte` base and ship from the `@viamrobotics/prime-ui/icons` subpath (`package.json` `exports["./icons"]`). The docs app aliases that subpath to source in dev, ahead of the bare package alias. `Icon` is `aria-hidden` by default and becomes `role="img"` when given `aria-label` or `aria-labelledby`. It emits no `data-testid`: a spec asserts the rendered `svg path`'s `d` against the same `@mdi/js` export. The old curated names map to `@mdi/js` exports in the migration table on the docs Icon page.

### Styling

Tailwind utility classes referencing `@viamrobotics/tailwind-config` tokens only (`bg-power-button-bright`, `text-heading`, `border-light`, …). Never hard-code color or spacing. New tokens go in `tailwind-config`'s `tailwind-config.css`, not here. Match the Viam design system at https://design.viam.com/, and see [.claude/rules/viam-context.md](../../.claude/rules/viam-context.md).

Four house rules on top of that:

- **No layout utilities on a root.** No `w-full`, no margins, no flex on the element the consumer gets `class` on. Svelte's array class syntax concatenates and Tailwind orders conflicting utilities by its own sort, so a consumer's `w-32` loses to a built-in `w-full`. The consumer owns width and placement. The exceptions are internal: `RadioGroup`'s `flex-col` / `flex-row` follows `orientation`, which drives keyboard semantics, and a part's own inner layout (`Input.Group`'s `inline-flex`, `RadioGroup.Item`'s `inline-flex`).
- **One focus treatment.** `@viamrobotics/tailwind-config` defines the component classes `focus-ring` (a 2px offset `focus-visible` outline) and `focus-ring-within` for a frame whose focus lives on a child, such as `Input.Group`, and the `input` class already carries `focus-ring`. Every focusable control wears one of them in its class list, and nothing else changes on focus. They are CSS, not a TS constant, so IntelliSense completes them and a consumer can put them on their own controls. They exist wherever the tokens are imported, and `styles.css` only imports the tokens and declares the `@source`. The design system documents no focus treatment, so this is prime's.
- **Token-named spellings.** `rounded-sm`, not bare `rounded`, even though the values match: `design.mjs check` reads the bare form as a literal.
- **No `!important`.** Precedence between a component's own states is expressed in selectors and source order, the way the `input` class lists error and warn before readonly and disabled so the later rule wins a tie, and a consumer can still override anything with a class.
- **Shared styling is a class in `@viamrobotics/tailwind-config`, not a TS constant.** `input`, `focus-ring`, and `focus-ring-within` are declared once as CSS there, and prime-ui adds none of its own, with their states as nested selectors on attributes the element already carries. A TS module that only holds a string of utilities gets no IntelliSense and hides CSS as code. A lookup table keyed by a prop value (`Icon/icon.ts` sizes, `Field/state.ts` icons) is logic and stays in TS.

### Doc comments

Open each component `.svelte` with an `@component` block: one-sentence description, a link to the bits-ui component if headless-backed, and a minimal `bind:` example. No prop docs there. Put those as `/** */` JSDoc on each `Props` field, with `@default` where the default is not obvious from the destructuring.

**These comments are the docs site.** The docs loader (`docs/src/loaders/prime-ui-components.ts`) renders the `@component` block as the component page's intro and builds the props table from the `Props` interface JSDoc, so:

- Write the block as markdown. Fenced ` ```svelte ` blocks become code samples.
- Link to a sibling component as `[`Select.Trigger`](./SelectTrigger.svelte)` or `[`Field`](../Field/Field.svelte)`. The loader rewrites those to docs links; they also work on editor hover.
- Name the interface `Props`. The loader only recognizes an `interface`, so a part with no own props still declares one (the `id` narrowing above gives it a member, which also keeps `@typescript-eslint/no-empty-object-type` quiet).
- A new root export in `index.ts` gets a collection entry automatically. The docs page under `docs/src/content/docs/packages/prime-ui/components/` is still yours to add.

## Tests

Co-located `*.svelte.spec.ts`, Vitest **browser mode** (`render` from `vitest-browser-svelte`, `userEvent` from `vitest/browser`, and portaled content like `Select` is queried on `document`). Spec files run serially (`fileParallelism: false` in `vite.config.ts`): they share one browser page, and parallel files fight over focus so `userEvent.keyboard` types into the wrong input. `vite.config.ts` uses the plain `@sveltejs/vite-plugin-svelte` plugin, and the package has no app framework.

A spec earns each case by failing when the behavior breaks, so the suite holds no case that restates a class list, counts exports, or re-tests the browser (a native number input stepping on ArrowUp). The conventions that keep it that way:

- **Styles are asserted as computed style, never as a class name.** `src/lib/__tests__/computed-style.ts` loads the Tailwind theme into the shared page and resolves a utility to the color it paints (`colorOf`), beside `borderColor`, `backgroundColor`, and `textColor` readers. A spec that reads any computed style imports it, or the bare `__tests__/tailwind.css`, so the theme is present even when the file runs alone. The one class-list check is the focus treatment, asserted as the `focus-ring` class on `Checkbox` and `RadioGroup.Item` and as the `input` class (which carries the ring) on `Input` and `Select.Trigger`, since focus-visible cannot be driven reliably from a test. `Input.Group`'s spec reads the group's computed `outlineWidth` instead, since a focused text input does match `:focus-visible`.
- **One rule over many inputs is an `it.each` table.** States, sizes, orientations, and the accept-or-veto pair of the controlled mode each read as one case table.
- **The `Field` cascade is tested once, in `Field/__tests__/Field.svelte.spec.ts`,** through `InputField.svelte` and `TextareaField.svelte` for the native inputs and `WidgetFields.svelte` for the widgets. A widget's own spec passes `state` directly and asserts its visual treatment. No per-widget `Error<X>` fixture.
- **For each value control, cover both binding modes with fixtures under `__tests__/` beside the spec:** `Bound<X>.svelte` (two-way `bind:`, taking the props a case needs such as `disabled`, `state`, or `name`), `Controlled<X>.svelte` (function binding with an `accept` prop toggling veto vs accept), and `Undefined<X>.svelte` (the owner's state starts `undefined`, which must not throw). A fixture that forwards a `state` prop destructures it as `state: fieldState`, since a local named `state` collides with the `$state` rune.
- **A `Select` spec closes the list in `afterEach`** (Escape when a `role="listbox"` is in the document), and a `Menu` spec does the same for `role="menu"`. A select unmounted while open leaves bits-ui reading destroyed deriveds and prints `derived_inert` warnings through the rest of the run.

## Tooling notes

- Imports are auto-sorted by `eslint-plugin-perfectionist` (`sort-imports`, natural order). Do not hand-order them, run `pnpm lint` or `pnpm format`.
- Never hand-fight Prettier/ESLint formatting. Run `format` and let it settle.
