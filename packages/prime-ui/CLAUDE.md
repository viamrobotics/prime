# @viamrobotics/prime-ui

Viam's Svelte 5 component library — the v2 of prime. Components wrap well-maintained **headless** primitives ([bits-ui](https://bits-ui.com)) or native elements, dressed in `@viamrobotics/tailwind-config` design tokens. Source lives in `src/lib/`. There is no app or playground in this package: the docs site ([apps/docs](../../apps/docs/)) is where components are demonstrated and where you look at them while developing.

## Layout

- `src/lib/` — published source. Add components here. `src/lib/index.ts` re-exports the public API.
- `dist/` — generated by `svelte-package` during `pnpm build`; what npm sees via the `files` field.

## Stack

| Layer         | Tool                                                                                |
| ------------- | ----------------------------------------------------------------------------------- |
| Framework     | Svelte 5 (runes). SvelteKit is present only as tooling: `svelte-package` and `sync` |
| Headless base | [bits-ui](https://bits-ui.com) (styled) + native elements                           |
| Bundler       | Vite                                                                                |
| Styles        | Tailwind CSS v4 + `@viamrobotics/tailwind-config` tokens                            |
| Tests         | Vitest (browser mode for `.svelte`)                                                 |
| Typecheck     | `svelte-check`                                                                      |
| Lint/format   | ESLint (+ `eslint-plugin-perfectionist`) + Prettier                                 |

## Workspace deps

`@viamrobotics/tailwind-config` is consumed via `workspace:^`. It's in `peerDependencies` (downstream consumers install it for tokens to resolve) and `devDependencies` (so the package resolves locally). At publish time pnpm rewrites `workspace:^` to a concrete range.

## Commands

Run from the repo root with a `--filter`, or from inside this package:

```bash
pnpm --filter @viamrobotics/prime-docs dev        # the component dev loop: docs site, hot-reloading this package's source
pnpm --filter @viamrobotics/prime-ui build        # svelte-package + publint
pnpm --filter @viamrobotics/prime-ui check        # svelte-check
pnpm --filter @viamrobotics/prime-ui test         # vitest, one shot
pnpm --filter @viamrobotics/prime-ui test:unit    # vitest, watch mode
pnpm --filter @viamrobotics/prime-ui lint         # prettier --check + eslint
pnpm --filter @viamrobotics/prime-ui format       # prettier --write
```

Root scripts (`pnpm build`, `pnpm check`, `pnpm lint`, `pnpm test`) fan these across the workspace.

`build`/`check`/`lint`/`test` (and the internal `sync`/`package` steps) are orchestrated by [wireit](https://github.com/google/wireit): each declares its inputs/outputs so unchanged work is skipped or restored from cache, locally and in CI. `sync` (`svelte-kit sync`) is a dependency of the others. To force a real re-run, prefix with `WIREIT_CACHE=none`.

## Where components are demonstrated

The docs site is the only consumer of demos. Every component has a page under `apps/docs/src/content/docs/packages/prime-ui/components/<slug>.mdx`, with its `Sandbox` demo and states showcase beside it in `<slug>/`. **A new component is not done until it has a docs page.**

`astro dev` aliases `@viamrobotics/prime-ui` to `src/lib/index.ts`, so edits here hot-reload into the docs with no build. `astro build` uses the package's `svelte` export (`dist`), so the published site renders what npm consumers get. The alias lives in `apps/docs/astro.config.mjs`.

## Authoring components

Follow [.claude/rules/svelte.md](../../.claude/rules/svelte.md) (runes only; typed `Props`; `$props()` with rest spread; `$derived` for computed classes — never `$effect`; `{@render children?.()}`; array/object class syntax).

### Public API — never leak the headless library

The public surface stays in **native / web-standard vocabulary**. Never surface a bits-ui prop or callback name (`onCheckedChange`, `onValueChange`, …): a consumer shouldn't need to learn bits-ui, and swapping the headless lib must not break the API. Extend the matching `svelte/elements` attribute type and `Omit` what you re-type or drop, e.g. `interface Props extends Omit<HTMLButtonAttributes, 'value'>`.

### State & binding (settled decision — don't regress)

Value/selection props are `$bindable`. Consumers manage state with **standard Svelte 5 bindings, not change callbacks**. Two supported modes:

- **Two-way** — `bind:checked` / `bind:value`. The default.
- **Fully controlled** — a `bind:` _function binding_: `bind:value={() => v, (next) => { … }}`. The setter is the source of truth, so it can transform or **veto** (don't write → nothing changes) and runs on every user-initiated change. To merely react (incl. programmatic changes), use `$effect`.

Two component flavors:

- **bits-ui widgets (`Checkbox`, `RadioGroup`, `Select`) are BIND-ONLY** — no change-callback prop. Declare `let { checked = $bindable(false) } = $props()` and put `bind:checked` straight on the bits-ui child; bits-ui carries controllability through untouched. Do **not** reintroduce synthesized DOM-event callbacks (`bind:ref` + a fabricated `currentTarget`) — that faked an event the widget never fires, and was removed on purpose.
- **native inputs (`Input`, `NumberInput`) keep native handlers** — they render a real `<input bind:value>`, so `oninput`/`onchange`/`onblur`/… pass through via `{...restProps}` for side effects, alongside `bind:value`. `NumberInput` bridges its `number | null` value onto `Input` with a function binding (`(next) => (value = next ?? null)`; empty field → `null`).

Full model + the non-obvious gotchas (Svelte can't detect if a prop is bound; native `bind:value` reads the input's runtime `type`) live in [apps/docs/src/content/docs/packages/prime-ui/components/state.mdx](../../apps/docs/src/content/docs/packages/prime-ui/components/state.mdx).

### Field — form parts expect to live in one

`Field` (`Field/Field.svelte`) is the form-field wrapper. It provides a context (`Field/useField.svelte.ts`: `provideField` / `useField`) carrying the control `id` (from `$props.id()` unless given), `disabled`, `required`, `state`, and two registries: labels (for `aria-labelledby`) and hints (for `aria-describedby`). Every form part reads it:

- `Label` → `for`, `required`, `disabled`, and registers its id.
- `Hint` → `disabled`, `state` (error turns `text-danger-dark`), and registers its id.
- `Input` / `NumberInput` / `Checkbox` / `RadioGroup` / `Select` + `Select.Trigger` → `id`, `disabled`, `required`, `state` where it applies, `aria-describedby`, and `aria-labelledby` on `RadioGroup` (a `role="radiogroup"` div is not labelable by `for`).

Rules when adding or changing a form part:

- **A prop passed directly always wins.** Declare the prop with no default (`disabled`, not `disabled = false`) and resolve `prop ?? field?.value ?? fallback` in a `$derived`. Svelte cannot tell "absent" from "undefined", so a default would shadow the field.
- **`useField()` returns `undefined` outside a `Field`.** Parts keep working standalone with explicit `id` / `for` / `aria-describedby`. Make it throw instead only as a deliberate decision.
- **Register from an `$effect`** (`$effect(() => field?.describe(id))`, the return value unregisters). The registry writes untracked so the effect does not depend on the list it appends to. Registration runs client-side only, so SSR output lacks `aria-describedby` until hydration.
- `Field` renders a bare `<div {...restProps}>` with no layout classes. Consumers pass `class`.

### Exports — single vs compound

`src/lib/index.ts` is the public API.

- **Single-part** → default-export directly: `export { default as Checkbox } from './Checkbox/Checkbox.svelte'`.
- **Multi-part** → a **compound** value in `<Folder>/<name>.ts` — `Object.assign` the parts onto the root with an **explicit `typeof` annotation**, then `export { Name }` from index:
  ```ts
  // Input/input.ts
  import Root from './Input.svelte';
  import StateIcon from './StateIcon.svelte';
  export const Input: typeof Root & { StateIcon: typeof StateIcon } = Object.assign(Root, {
  	StateIcon
  });
  ```
  This gives both `<Input>` and `<Input.StateIcon>`. The annotation is **required**: a bare `Object.assign` (or object literal) makes `svelte-package` inline the inferred type, hit each component's un-exported `Props`, and fail d.ts emit with _"cannot be named"_. The `typeof` query defers it. Keep the barrel minimal — no helpers/maps/state modules.

### Icon

`Icon` takes an `icon` prop: a curated Viam icon name (see `Icon/icons.ts`) **or** any Svelte icon component (rendered directly). Add curated names to `iconMap`; bring-your-own components tree-shake to only what's used.

### Styling

Tailwind utility classes referencing `@viamrobotics/tailwind-config` tokens only (`bg-power-button`, `text-heading`, `border-light`, …) — never hard-code color/spacing. New tokens go in `tailwind-config`'s `tailwind-config.css`, not here. Match the Viam design system (https://design.viam.com/; see [.claude/rules/viam-context.md](../../.claude/rules/viam-context.md)).

### Doc comments

Open each component `.svelte` with an `@component` block: one-sentence description, a link to the bits-ui component if headless-backed, and a minimal `bind:` example. No prop docs there — put those as `/** */` JSDoc on each `Props` field, with `@default` where the default is not obvious from the destructuring.

**These comments are the docs site.** The docs loader (`apps/docs/src/loaders/prime-ui-components.ts`) renders the `@component` block as the component page's intro and builds the props table from the `Props` interface JSDoc, so:

- Write the block as markdown. Fenced ` ```svelte ` blocks become code samples.
- Link to a sibling component as `[`Select.Trigger`](./SelectTrigger.svelte)` or `[`Field`](../Field/Field.svelte)`. The loader rewrites those to docs links; they also work on editor hover.
- Name the interface `Props`. A part that takes an external type straight (`Select.TriggerProps = $props()`) is documented as "Takes `Select.TriggerProps` as its props" with no table.
- A new root export in `index.ts` gets a collection entry automatically. The docs page under `apps/docs/src/content/docs/packages/prime-ui/components/` is still yours to add.

## Tests

Co-located `*.svelte.spec.ts`, Vitest **browser mode** (`render` from `vitest-browser-svelte`, `userEvent` from `vitest/browser`; portaled content like `Select` is queried on `document`). Spec files run serially (`fileParallelism: false` in `vite.config.ts`): they share one browser page, and parallel files fight over focus so `userEvent.keyboard` types into the wrong input. `vite.config.ts` uses the plain `@sveltejs/vite-plugin-svelte` plugin, not `sveltekit()`, which would need an `src/app.html` to serve the test page. For each value control, cover both modes with fixtures under `__fixtures__/`: `Bound<X>.svelte` (two-way `bind:`) and `Controlled<X>.svelte` (function binding with an `accept` prop toggling veto vs accept).

- Never hand-fight Prettier/ESLint formatting; run `format` and let it settle.
