# @viamrobotics/prime-ui

Viam's Svelte 5 component library, the v2 of prime. Components live in `src/lib/`. `src/routes/` is a showcase and dev sandbox, not part of the published artifact.

[ROADMAP.md](ROADMAP.md) tracks the v2 migration: a component-by-component inventory of what carries forward from v1 and what each is replaced by.

## Layout

- `src/lib/` published source. Add components here. `src/lib/index.ts` re-exports the public API.
- `src/routes/` SvelteKit playground app. Dev sandbox locally, built statically and embedded under [apps/docs](../../apps/docs/) at `/playground/prime-ui/` for the deployed docs site. Not published.
- `dist/` generated by `svelte-package` during `pnpm build`. What npm sees via the `files` field.
- `build/` generated by `vite build` (static SvelteKit output). Gitignored, consumed by [apps/docs/scripts/build-playgrounds.mjs](../../apps/docs/scripts/build-playgrounds.mjs).

## Stack

Svelte 5 runes via SvelteKit, `@sveltejs/adapter-static` for the playground bundle, Vite, Tailwind CSS v4 with tokens from `@viamrobotics/tailwind-config`, Vitest (browser mode for `.svelte`), `svelte-check`, ESLint, Prettier.

`@viamrobotics/tailwind-config` is consumed via `workspace:^`. It sits in `peerDependencies` (downstream consumers install it for tokens to resolve) and in `devDependencies` (so this package's own build and showcase can `@import '@viamrobotics/tailwind-config'`). pnpm rewrites `workspace:^` to a concrete `^X.Y.Z` range at publish time.

## Commands

```bash
pnpm --filter @viamrobotics/prime-ui dev          # start showcase dev server
pnpm --filter @viamrobotics/prime-ui build        # vite build + svelte-package + publint
pnpm --filter @viamrobotics/prime-ui check        # svelte-check
pnpm --filter @viamrobotics/prime-ui test         # vitest, one shot
pnpm --filter @viamrobotics/prime-ui test:unit    # vitest, watch mode
pnpm --filter @viamrobotics/prime-ui lint         # prettier --check + eslint
pnpm --filter @viamrobotics/prime-ui format       # prettier --write
```

The root scripts (`pnpm build`, `pnpm check`, `pnpm lint`, `pnpm test`) fan these out across the workspace.

`build`, `check`, `lint`, `test`, and the internal `sync`, `vite-build`, and `package` steps are orchestrated by [wireit](https://github.com/google/wireit). Each declares its inputs and outputs so unchanged work is skipped or restored from cache, locally and in CI. `sync` (`svelte-kit sync`) is a dependency of the others. `WIREIT_CACHE=none` forces a real re-run.

## Static build and playground deployment

`svelte.config.js` derives `paths.base` from the `DOCS_BASE` env var plus this package's own `/playground/prime-ui` segment, so one build works at every deploy path:

| `DOCS_BASE`                 | resulting base                                 |
| --------------------------- | ---------------------------------------------- |
| unset (local, npm)          | `/`                                            |
| `/prime/`                   | `/prime/playground/prime-ui`                   |
| `/prime/pr-preview/pr-<N>/` | `/prime/pr-preview/pr-<N>/playground/prime-ui` |

The docs build sets `DOCS_BASE` and builds this playground first, since it is a wireit dependency of the docs `build:playgrounds` script. [apps/docs/scripts/build-playgrounds.mjs](../../apps/docs/scripts/build-playgrounds.mjs) then copies the output into place. A raw `BASE_PATH` still works as a fallback override.

Every route must be prerenderable. `src/routes/+layout.ts` enforces it with `export const prerender = true`. A route that cannot prerender fails the static build, so either make it prerenderable or keep it out of the playground.

## Conventions

- Svelte 5 runes only, no Svelte 4 syntax. See [.claude/rules/svelte.md](../../.claude/rules/svelte.md).
- Components use Tailwind utility classes referencing tokens from `@viamrobotics/tailwind-config` (`bg-power-button`, `text-heading`). Never hard-code a color or spacing value.
- New design tokens belong in `@viamrobotics/tailwind-config`'s `tailwind-config.css`, not in components.
- Token values and component patterns must match the Viam design system at https://design.viam.com/. See [.claude/rules/design-system.md](../../.claude/rules/design-system.md).
