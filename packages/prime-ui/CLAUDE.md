# @viamrobotics/prime-ui

Viam's Svelte 5 component library, the v2 of prime. Components wrap well-maintained **headless** primitives ([bits-ui](https://bits-ui.com), and [zag](https://zagjs.com) where bits-ui has no equivalent, such as the toast) or native elements, dressed in `@viamrobotics/tailwind-config` design tokens. Source lives in `src/lib/`. There is no app in this package: the docs site ([docs](../../docs/)) is where components are demonstrated and where you look at them while developing.

## Layout

- `src/lib/`: published source. Add components here. `src/lib/index.ts` re-exports the public API.
- `dist/`: generated by `svelte-package` during `pnpm build`. It is what npm sees via the `files` field.

## Stack

| Layer         | Tool                                                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Framework     | Svelte 5 (runes). `svelte-package` builds `dist`, with no app framework                                                         |
| Headless base | [bits-ui](https://bits-ui.com) (styled), [zag](https://zagjs.com) for the toast machine and `clickOutside`, and native elements |
| Bundler       | Vite                                                                                                                            |
| Styles        | Tailwind CSS v4 + `@viamrobotics/tailwind-config` tokens                                                                        |
| Tests         | Vitest (browser mode for `.svelte`)                                                                                             |
| Typecheck     | `svelte-check`                                                                                                                  |
| Lint/format   | ESLint (+ `eslint-plugin-perfectionist`) + Prettier                                                                             |

## Workspace deps

`@viamrobotics/tailwind-config` is a regular `dependencies` entry at `workspace:^`, which pnpm rewrites to a concrete caret range at publish time. It is not a peer dependency on purpose: changesets bumps a package to major whenever one of its peers gets a minor bump, so a token addition in tailwind-config would major every component package. A consumer that also installs tailwind-config directly dedupes to one copy while the ranges overlap, and a second copy of a tokens-only stylesheet redefines the same custom properties to the same values.

`@internationalized/date` is a bits-ui peer dependency and the date model of `DatePicker` and `DateRangePicker`, whose `min` and `max` are its `DateValue`. A `DatePicker` value is one `DateValue`, and a `DateRangePicker` value is a `DateRange` holding a `start` and an `end`. The package stays in `dependencies` so bits-ui resolves it without every consumer installing it by hand. A consumer that constructs dates installs it too.

## Authoring components

Follow [.claude/rules/svelte.md](../../.claude/rules/svelte.md): runes only, a typed `Props`, `$props()` with a rest spread, `$derived` for computed classes and never `$effect`, `{@render children?.()}`, and array or object class syntax.

### Public API: never leak the headless library

The public surface stays in **native / web-standard vocabulary**. Never surface a bits-ui prop or callback name (`onCheckedChange`, `onValueChange`, …): a consumer shouldn't need to learn bits-ui, and swapping the headless lib must not break the API. Extend the matching `svelte/elements` attribute type and `Omit` what you re-type or drop, e.g. `interface Props extends Omit<HTMLButtonAttributes, 'value'>`. This applies to every part of a compound too: never type a part's props as `Select.TriggerProps` or another bits-ui export. bits-ui requires `id` to be a string and floating content's `dir` to be `ltr` or `rtl`, so a part that spreads onto a bits-ui element narrows those two fields in its `Props` with a one-line doc saying why.

### One `class`, one root, decoration is a snippet

A component is atomic: `class` lands on its root element and that is the only class prop. A root that renders a region takes the element's other attributes through a rest spread placed before its own, so its own attributes win. Never add a second class prop for an inner element (`inputClass`, `iconClass`, …). An internal decoration the consumer may want to resize, recolor, or replace (a checkbox or radio icon, a trigger chevron, a required asterisk) is an optional snippet prop with the default rendered in its `{:else}`: `indicator?: Snippet<[{ checked: boolean }]>` on `RadioGroup.Item`, `indicator?: Snippet` on `Select.Trigger` and `Label`, `indicator?: Snippet<[{ checked: boolean }]>` on `Menu.CheckboxItem` and `Menu.RadioItem`, `chevron?: Snippet` on `Menu.SubTrigger`, `children` on `Checkbox` since it has nothing else inside. Render the default inline in the `{:else}` branch. Do not declare a `{#snippet}` inside an `{#if}` to pass it to a bits-ui component: a snippet is only a prop of the component when it is a direct child of its tag, anywhere else it is a local declaration nothing renders, with untyped parameters.

### State & binding

Value/selection props are `$bindable`. Consumers manage state with **standard Svelte 5 bindings, not change callbacks**. Two supported modes:

- **Two-way**: `bind:checked` / `bind:value`. The default.
- **Fully controlled**: a `bind:` _function binding_, `bind:value={() => v, (next) => { … }}`. The setter is the source of truth, so it can transform or **veto** (no write means no change) and runs on every user-initiated change. To merely react, including to programmatic changes, use `$effect`.

Two component flavors:

- **bits-ui widgets (`Checkbox`, `Switch`, `RadioGroup`, `ToggleButtons`, `Select`, `MultiSelect`, `Combobox`, `DatePicker`, `DateRangePicker`, `Collapsible`, `Tabs`, `Menu.CheckboxItem`, `Menu.RadioGroup`) are BIND-ONLY**, with no change-callback prop. Declare the prop with **no fallback** (`let { checked = $bindable() } = $props()`) and bridge to the bits-ui child with a function binding that supplies the fallback (`bind:checked={() => checked ?? false, (next) => (checked = next)}`). A `$bindable(false)` fallback throws Svelte's `props_invalid_value` when a consumer binds state that starts `undefined`, and bits-ui's own `Checkbox` and `RadioGroup` carry fallbacks too, so `undefined` must never reach them through `bind:`. No synthesized DOM-event callbacks: a widget fires no `change` or `input`, so nothing fabricates one.
- **native inputs (`Input`, `NumberInput`, `Textarea`) keep native handlers**: each renders one real `<input bind:value>` (or `<textarea>`), so `oninput`/`onchange`/`onblur`/… pass through via `{...restProps}` for side effects, alongside `bind:value`. `Input.value` is a `string`, and its `type` admits only the native types whose value is a string (`number`, `range`, `checkbox`, `radio`, and `file` are excluded, since Svelte binds them differently). `NumberInput` renders its own `<input type="number">` with `value?: number` and a `step` that admits the native `'any'`. It is a compound (`Input/number-input.ts`) with one part, `NumberInput.Stepper` (`Input/NumberInputStepper.svelte`), which mirrors the browser's spin buttons: a primary press calls the input's `stepUp()` or `stepDown()` and dispatches bubbling `input` and `change`, a held press repeats after 400ms every 60ms, and the buttons are `aria-hidden` with `tabindex="-1"` and cancel `pointerdown` so focus stays put. Standalone, `NumberInput` renders an `Input.Group` frame holding the input and a stepper, `class` lands on that frame, and every other attribute lands on the input. `Input.Group` provides a context (`Input/useInputGroup.ts`), and a `NumberInput` inside one renders the bare input with `class` on it, and the consumer places `NumberInput.Stepper` as the group's last child. The stepper finds the input as its frame's direct `input[type="number"]` child. Its in-flow spacer reserves its place, and its box is absolutely positioned against the frame (the group is `relative`) and inherits the frame's right padding, so it meets the border at full height in any frame size. It reads the frame through the group's `group/input` name: hover or focus within shows it, `pointer-coarse:` always shows it, and a `:disabled` or `readonly` input hides it. The input hides the browser's spin buttons only while its group holds a `[data-number-stepper]`. A specialized input component is warranted only when the value type differs (`NumberInput`) or native UI is missing (date and time fields, pin input). Otherwise it is `Input` with a `type`, never a `TextInput` or `PasswordInput` beside it. `Textarea` is the multi-line one, growing with its content through `field-sizing: content` with `rows` as the fallback. An empty `NumberInput` is `undefined`. A string-valued control starts `undefined` and binds `''` once the user has cleared it, which is what Svelte's `bind:value` yields there. All three, and `FileInput`, spread one attribute bag from `Input/useInputControl.svelte.ts` after their rest props, so their Field wiring never drifts, and all three wear the `input` class from `@viamrobotics/tailwind-config`, which reads `disabled`, `readonly`, `aria-invalid`, and `data-field-state` off the element. Adornments (a leading icon, a unit suffix, `Field.StateIcon`) go in an `Input.Group` (`Input/InputGroup.svelte`): it wears the same `input` class, whose `& > input` rule strips the inner input's border, padding, and background and whose `:has(> input…)` alternatives restyle the group from the input's attributes, so restyling runs no JavaScript. It forwards a pointer-down on its padding or on non-interactive content to the input, and leaves a press on any element matching `INTERACTIVE_DESCENDANT_SELECTOR` from `src/lib/interactive-descendant.ts` alone, the list `Tooltip.Trigger` also uses to find the control it describes. No `!important` anywhere: precedence is expressed in the selectors.
- **`FileInput` is the native input that needs a wrapper.** `Input/FileInput.svelte` renders a real `<input type="file">` stretched invisibly over a frame that wears the `input` class, so the picker, a dropped file, the keyboard, and form submission stay the browser's, while the frame draws the prompt, the chosen names, and a clear button. `class` lands on the frame and every other attribute, `accept`, `multiple`, and `onchange` among them, on the input. `value` is a `File[]`, starts `undefined`, and binds `[]` once cleared. A native file input cannot be written through `bind:value`, so the component copies a value written from outside, or one a function binding refused, to the input's `files` through the helpers in `Input/file-list.ts`. A form reset fires no `change`, so the component listens for the form's `reset` and writes `[]`. The frame takes its states from the input through the `input` class's `:has(> input…)` rules, like `Input.Group`. The prompt is `aria-hidden` decoration replaced through `children`, and the clear button is a direct child of the frame, so the frame's `focus-ring-within` is its focus indicator.
- **widgets still forward DOM handlers.** `Checkbox`, `RadioGroup.Item`, and `Select.Trigger` render a real `<button>`, and bits-ui composes a consumer `onfocus`/`onblur`/`onclick`/`onkeydown` with its own (consumer first, `preventDefault` stops bits-ui's). What never fires is `change`/`input`, since no native control changes: that is the reason for bind-only, not a lack of pass-through. `focus`/`blur` do not bubble, so a group-level listener on `RadioGroup` is `onfocusin`/`onfocusout`. `Select` renders no element: its `Props` is a plain interface with no HTML attributes, so a handler or `class` on `<Select>` is a type error instead of a silent drop. They belong on `Select.Trigger`.

The full model, including the two edge cases (Svelte cannot detect if a prop is bound, and native `bind:value` reads the input's runtime `type`), lives in [docs/src/content/docs/packages/prime-ui/components/state.mdx](../../docs/src/content/docs/packages/prime-ui/components/state.mdx).

### Field: form parts expect to live in one

`Field` (`Field/Field.svelte`) is the form-field wrapper and the state manager for everything inside it. Every form control renders inside one, and `Field` requires its name by the `AccessibleName` union (`src/lib/accessible-name.ts`): a `label`, an `aria-label`, or an `aria-labelledby`. `Props` follows the `Tabs.List` pattern, an `interface Props` that omits `aria-label` and `aria-labelledby` from the element attributes and a `$props()` typed `Props & AccessibleName`, since the docs loader reads only the interface. The name never lands on the wrapper div. It provides a context (`Field/useField.svelte.ts`: `provideField` / `useField`, with the `FieldContext` type in `Field/context.ts`) carrying `controlId` (the id it assigns to the control, from `$props.id()` unless the `controlId` prop is given, while a plain `id` lands on the wrapper div like any attribute), `disabled`, `required`, `state` (a `FieldState` from `Field/state.ts`: `none`, `info`, `warn`, `error`, with the `fieldState.is*` type guards beside it for a narrowed check), the name as `labelText`, `ariaLabel`, and `ariaLabelledBy`, and two registries: labels (for `aria-labelledby`) and hints (for `aria-describedby`). Every form part reads it:

- `Label` → `for`, `required`, `disabled`, and registers its id. With no `children` it renders the field's `label`.
- `Hint` → `disabled`, `state` (`error`, `warn`, and `info` each color the text), and registers its id.
- `Field.StateIcon` (`Field/StateIcon.svelte`, the compound part) → `state`, rendering the matching icon or nothing. It takes a `state` prop standalone. Place it where the layout wants it, usually inside an `Input.Group`.
- `Input` / `NumberInput` / `Textarea` / `FileInput` / `Checkbox` / `Switch` / `RadioGroup` / `ToggleButtons` / `Select.Trigger` (shared by `MultiSelect`) / `Combobox.Input` / `DatePicker.Field` / `DateRangePicker.Field` → the name, through `controlName` in `Field/useField.svelte.ts`: `aria-labelledby` from the placed Labels' ids, else the field's `aria-labelledby`, else the field's `label` or `aria-label` as `aria-label`. A control's own `aria-label` or `aria-labelledby` replaces all of it.
- `Input` / `NumberInput` / `Textarea` / `FileInput` / `Checkbox` / `Switch` / `RadioGroup` / `ToggleButtons` / `Select` / `MultiSelect` + `Select.Trigger` / `Combobox` + `Combobox.Input` / `DatePicker` + `DatePicker.Field` / `DateRangePicker` + `DateRangePicker.Field` → `id`, `disabled`, `required`, `state`, and `aria-describedby`. A `role="radiogroup"` div (`RadioGroup`, `ToggleButtons`) or `role="group"` div (`DatePicker.Field`, `DateRangePicker.Field`) is not labelable by `for`, so the name always lands as `aria-label` or `aria-labelledby` there. Every control sets `aria-invalid` on `error`: the inputs, `Select.Trigger`, `Combobox.Input`, `DatePicker.Field`, and `DateRangePicker.Field` turn their border through the shared `input` class, which keys on `aria-invalid` and `data-field-state`, the checkbox and radio indicators turn `text-danger-dark` (radio items through `group-aria-invalid:` off the group root), and each `ToggleButtons` item turns its border `danger-dark` through `group-aria-invalid:enabled:` off the group root. `DatePicker.Field` and `DateRangePicker.Field` also set `aria-invalid` and `aria-required` on each segment, since a `role="group"` supports neither.
- `Progress`, `StatusDot`, `Popover.Content`, and the icon-only `Dialog.Close`, `Popover.Close`, `Takeover.Close`, and `Banner.Close` require a name by the same `AccessibleName` union. A Close given `children` is named by their text and needs none.

Rules when adding or changing a form part:

- **A prop passed directly always wins.** Declare the prop with no default (`disabled`, not `disabled = false`) and resolve `prop ?? field?.value ?? fallback` in a `$derived`. Svelte cannot tell "absent" from "undefined", so a default would shadow the field.
- **`useField()` returns `undefined` outside a `Field`.** Parts keep working standalone with explicit `id` / `for` / `aria-describedby`. Make it throw instead only as a deliberate decision.
- **A form control warns in development when it renders unnamed.** `src/lib/accessible-name-warning.ts` gates on `DEV` from `esm-env` and checks the rendered element after pending updates settle: a non-empty `aria-label`, an `aria-labelledby`, or a non-empty `labels` list. It never checks for a `Field`, so a control named by `<label for>` or an `aria-*` prop outside any field stays silent. Attach it to the element that carries the name, `{@attach accessibleNameWarning('Input')}`, or call `warnIfUnnamed(element, 'Input')` from a `$effect` once a `bind:ref` is set, as `Checkbox`, `Switch`, `RadioGroup`, `ToggleButtons`, and `Select.Trigger` do for the bits-ui roots.
- **Register from an `$effect`** (`$effect(() => field?.describe(id))`, the return value unregisters). The registry writes untracked so the effect does not depend on the list it appends to. Registration runs client-side only, so SSR output lacks `aria-describedby` until hydration.
- `Field` renders a bare `<div {...restProps}>` with no layout classes. Consumers pass `class`.

### Exports: single vs compound

`src/lib/index.ts` is the public API.

- **Single-part** → default-export directly: `export { default as Checkbox } from './Checkbox/Checkbox.svelte'`.
- **Multi-part** → a **compound** value in `<Folder>/<name>.ts`: `Object.assign` the parts onto the root with an **explicit `typeof` annotation**, then `export { Name }` from index:
  ```ts
  // Field/field.ts
  import Root from './Field.svelte';
  import StateIcon from './StateIcon.svelte';
  export const Field: typeof Root & { StateIcon: typeof StateIcon } = Object.assign(Root, {
  	StateIcon
  });
  ```
  This gives both `<Field>` and `<Field.StateIcon>`. The annotation is **required**: a bare `Object.assign` (or object literal) makes `svelte-package` inline the inferred type, hit each component's un-exported `Props`, and fail d.ts emit with _"cannot be named"_. The `typeof` query defers it. Public types live in a sibling `.ts` named for their domain (`Field/state.ts`, `Combobox/filter.ts`, `Banner/variant.ts`, `portal.ts`), never in a `.svelte.ts` runtime module. Keep the barrel minimal, with no helpers, maps, or state modules. The docs loader parses the barrel: each part must be imported as `import Part from './Part.svelte'` from the **same folder**, and listed in the `Object.assign` object as shorthand. A compound that loses its `Object.assign` is silently dropped from the docs, so repoint `index.ts` at the `.svelte` file when a component goes single-part.

A root that owns data its parts render shares it through a context module beside the barrel, the way `Select` shares `items` through `Select/useSelect.svelte.ts` so `Select.Items` can render one `Select.Item` per entry. `items` is the single source of truth there: bits-ui reads it for the closed trigger's label and, in single mode, for typeahead while the list is closed. `MultiSelect` gets no closed-list typeahead, and arrow keys on a closed trigger open the list in both modes. Without it, the closed trigger shows an initial value's raw value until the list mounts, so keep it on the root. `Combobox` shares the `matches` its `filter` keeps for the typed `query`, and the text its input shows through `Combobox/useCombobox.svelte.ts`, so `Combobox.Items` renders the matches and `Combobox.Empty` shows only when there are none.

### Menu, Banner, and Toast

`Menu.Content` and `ContextMenu.Content` are named by their trigger by default, with `aria-labelledby` pointing at the trigger id through `Menu/useTriggerName.svelte.ts`, unless the consumer passes `aria-label` or `aria-labelledby`. `Banner` and `Toast` add no text of their own: the variant is styling and a live-region role, the tone chip stays `aria-hidden`, and content that needs its tone announced says so itself.

### ToggleButtons and Tabs

`ToggleButtons` is bits-ui's single-select `ToggleGroup`, which renders the items as `role="radio"` with `aria-checked` inside a `role="radiogroup"` (rendered through bits-ui's `child` snippet, since the root's own `role="group"` outranks a prop) and no `aria-pressed`. One option is always selected: the bridge's setter ignores bits-ui's empty write when the selected item is clicked again. The one Tab stop is the selected option when it is enabled (`useToggleButtons.svelte.ts` tells each item whether a selection exists, and the item overrides bits-ui's roving `tabindex`), otherwise bits-ui's default. The root wears `button-group`, which joins the items into one row. `ToggleButtons.Item` carries its own colors keyed on `data-state="on"` rather than the `button` class, whose `:hover` rule outranks a utility on the same element.

`Tabs` is compositional like every other compound: `Tabs.List` holds one `Tabs.Trigger` per tab and `Tabs.Content` is the panel. Each trigger registers its `value` and its element with the root context (`Tabs/useTabs.svelte.ts`) in mount order. A selection whose tab is gone, or a bound `value` that names no tab, falls back to the leftmost remaining tab by document position, since mount order drifts from strip order after a move or a front insert. A strip with one tab is the consumer's `{#if}` around `Tabs.List`. Each trigger renders through bits-ui's `child` snippet as a `<div role="tab">` so a control inside it (a close `icon-button`) is valid HTML. The same wrapper drops bits-ui's `type="button"` and lets a key event from a nested control pass bits-ui's handler, which would otherwise swallow Enter and Space. Controls nested in a tab go through the `actions` snippet, rendered after a `display: contents` label span. The tab gets `aria-labelledby` pointing at that span when `actions` or `status` is passed or the list is `closable`, and the consumer gave no `aria-label` or `aria-labelledby`. A consumer control stops click propagation itself so the click does not select the tab. The built-in close and move buttons do so on their own. An underline-variant disabled tab keeps `text-disabled-dark`, under WCAG 1.4.3's exemption for inactive controls, while the file variant's disabled tab uses `text-subtle-2`.

`Tabs` takes `variant` (`'underline'` by default, or `'file'`), shared through the root context, and each part maps it to a `tailwind-config` class, with a consumer `class` appended last. `underline` renders the list as `underline-tabs` and each trigger as `underline-tab`. `file` renders the list as `file-tabs`, each trigger as `file-tab`, and the drag landing cell as `file-tab-slot`. The list and the triggers carry no inline variant utilities. Under `underline`, the drag landing cell keeps its layout utilities inline in `LandingChip`. A part rendered with no root behaves as `underline`. `underline-tab` applies the shared `focus-ring`, so no trigger wears it directly. `file-tab` draws its own inset focus ring instead, because the strip's scroll container would clip an outside ring. When a file-style tab becomes selected it adjusts the list's own `scrollLeft` to stay in view, never `scrollIntoView`, which can scroll the page.

Reordering is off unless `Tabs.List` takes `reorderable`, and it works under both variants. The order is the consumer's state: `Tabs.List` takes a bindable `order`, the tab values in strip order, declared with no fallback like every bind-only prop, and the consumer renders its triggers from it in a keyed `{#each}`, since the component cannot move markup it does not own. A move writes a new array and never mutates the old one. With `order` unset, a move starts from the triggers' registration order. A function binding can refuse a move: after the write the list reads `order` back, and an unchanged order leaves the strip, the focus, and the announcement as they were. Selection is untouched, since a move changes no `value`. A disabled tab cannot be moved, and other tabs move past it. Moving past either end does nothing. Setting `reorderable` or `closable` while `order` is undefined logs a development warning, and moves and closes still write the list's own `order`.

- **Keys.** Alt+Shift+ArrowLeft and Alt+Shift+ArrowRight on a focused tab move it one place, the chord prime-panes uses, and every movable tab says so through `aria-keyshortcuts`. The trigger handles the chord before bits-ui's roving focus sees the arrow. Focus stays on the moved tab, restored after the keyed `{#each}` moves its node.
- **Announcement.** A reorderable or closable list renders a visually hidden `role="status"` region as a sibling after the tablist, never inside it. A close says `<label> closed.` A move says `<label> moved to position <n> of <total>.`, prime-panes' wording, where the label is the text of the element named by `aria-labelledby`, then the tab's `aria-label`, then its trimmed text. The ghost shows the visible label span.
- **Pointer.** A primary press on a movable tab, outside any interactive descendant (`INTERACTIVE_DESCENDANT_SELECTOR` in `src/lib/interactive-descendant.ts`), becomes a drag once the pointer travels 4px. A touch press must first hold 250ms without traveling, since a touch that moves early is scrolling the strip, and once armed it blocks scrolling for the rest of the press. While dragging, the lifted tab leaves the strip, a ghost with its label follows the pointer, and an `aria-hidden` info chip holds the slot where it will land. Near either end of a scrolling strip the strip scrolls. Escape, a lost pointer, or the lifted tab unmounting cancels with no write. Escape is consumed only while a drag is under way, so during a press that never became a drag it still reaches an enclosing dialog. A drop writes `order` through the same path as a key, announcement included, and swallows the click that follows it. A drag alone fails WCAG 2.5.7, so `actions` receives `movePrevious`, `moveNext`, `canMovePrevious`, and `canMoveNext`, which take the same path as a key, for Move left and Move right controls. `Tabs.MovePrevious` and `Tabs.MoveNext` are those controls built in. They read a per-trigger context (`Tabs/useTabsTrigger.svelte.ts`) and carry `tabindex="-1"`, since the chord covers the keyboard.
- **Close.** `Tabs.List` takes `closable`. Each tab that is not disabled renders a close `icon-button` with `tabindex="-1"`, named `Close <label>`, after the `actions`. The button shows on the selected tab and on a hovered one, and keeps its space through `visibility` elsewhere. The trigger's `status` snippet shares that cell and shows while the button is hidden, or always on a list that is not closable, and it describes the tab through `aria-describedby`. Delete on a focused tab closes it, and `aria-keyshortcuts` lists `Delete` before the move chords. A close writes `order` without the tab, reads it back like a move so a function binding can refuse, announces, and moves focus to the newly selected tab when focus was inside the closed one. The tablist stays one Tab stop, and only consumer controls in `actions` keep theirs.

### Icon

`Icon` takes an `icon` prop: an SVG path string (an `@mdi/js` export, drawn on a 24×24 viewBox) **or** any Svelte icon component, rendered directly. prime-ui ships no map of icon names. mdi is what the Viam app renders, so consumers bring `@mdi/js`, and internal parts import the few paths they use (`mdiChevronDown`, `mdiCheck`, …) rather than a shared map. The hand-drawn Viam glyphs live in `src/lib/Icon/icons/` as components over an internal `Glyph.svelte` base and ship from the `@viamrobotics/prime-ui/icons` subpath (`package.json` `exports["./icons"]`). The docs app aliases that subpath to source in dev, ahead of the bare package alias. `Icon` is `aria-hidden` by default and becomes `role="img"` when given `aria-label` or `aria-labelledby`. It emits no `data-testid`: a spec asserts the rendered `svg path`'s `d` against the same `@mdi/js` export. prime-core's curated names map to `@mdi/js` exports in the Icons section of the docs "Migrating from prime-core" page.

### Utilities: attachments and the keybindings subpath

Function exports live beside the components. `src/lib/attachments/` holds Svelte attachments, and `clickOutside` (over `@zag-js/interact-outside`) ships from the root barrel. A press inside the element does not count as outside. Neither does a press inside open, non-modal content the element opens into a portal and links through `aria-controls`, such as a `Popover` or `Menu` whose trigger is inside it. A `Dialog` is modal, so a press in it counts as outside. `Popover.Content` never traps focus. Tab from its last control moves to the tabbable after the trigger, and Shift+Tab from its first control returns to the trigger, through `Popover/tab-order.ts`. `src/lib/keybindings/` is the shortcut registry, re-exported from the root barrel through its own `index.ts`: `provideKeybindings` creates the registry and owns the one capture-phase window `keydown` listener, `useHotkey` registers a shortcut for as long as its component is mounted, and `formatKeybinding` / `keybindingParts` print one for a label. `Keybinding.group` is a free string. The types live in `keybindings/keybinding.ts`, never in the `.svelte.ts` module. A utility gets a docs page under `docs/src/content/docs/packages/prime-ui/utilities/`.

### Styling

Tailwind utility classes referencing `@viamrobotics/tailwind-config` tokens only (`bg-power-button-bright`, `text-heading`, `border-light`, …). Never hard-code color or spacing. New tokens go in `tailwind-config`'s `tailwind-config.css`, not here. Match the Viam design system at https://design.viam.com/, and see [.claude/rules/viam-context.md](../../.claude/rules/viam-context.md).

Six house rules on top of that:

- **No layout utilities on a root.** No `w-full`, no margins, no flex on the element the consumer gets `class` on. Svelte's array class syntax concatenates and Tailwind orders conflicting utilities by its own sort, so a consumer's `w-32` loses to a built-in `w-full`. The consumer owns width and placement. The exceptions are documented ones that do the part's own job. `RadioGroup`'s `flex-col` / `flex-row` follows `orientation`, which drives keyboard semantics, and its description wrapper carries `flex flex-col`. `Switch` carries `shrink-0` and `inline-flex`, `Menubar`'s root carries `flex`, and a part's own inner layout covers `Input.Group`'s `inline-flex` and `RadioGroup.Item`'s `inline-flex`. A margin a class carries onto a root, such as `underline-tab`'s `-mb-px`, counts the same way. A floating panel sized to its anchor or the viewport (the `Select`, `Combobox`, `Menu`, `Tooltip`, and `Dialog` content parts) and a part sized by a prop or laying out its own content (`Icon`'s `size`, `Label`, `Breadcrumbs.Ellipsis`, `Menu.Shortcut`, `Menu.Separator`) keep their width and layout utilities too.
- **One focus treatment.** `@viamrobotics/tailwind-config` defines the component classes `focus-ring` (a 2px offset `focus-visible` outline) and `focus-ring-within` for a frame whose focus lives on a child, such as `Input.Group`, and the `input` class already carries `focus-ring`. Every focusable control wears one of them in its class list, and nothing else changes on focus. They are CSS, not a TS constant, so IntelliSense completes them and a consumer can put them on their own controls. They exist wherever the tokens are imported, and `styles.css` only imports the tokens and declares the `@source`. The design system documents no focus treatment, so this is prime's. The one exception is a segmented field: `DatePicker.Field` and `DateRangePicker.Field` fill the focused segment with `bg-medium`, because the fill marks which segment the keys edit, like a caret, while the frame alone carries the focus ring.
- **Token-named spellings.** `rounded-sm`, not bare `rounded`, even though the values match: `design.mjs check` reads the bare form as a literal.
- **No `!important`.** Precedence between a component's own states is expressed in selectors and source order, the way the `input` class lists error and warn before readonly and disabled so the later rule wins a tie, and a consumer can still override anything with a class.
- **Shared styling is a class in `@viamrobotics/tailwind-config`, not a TS constant.** `input`, `focus-ring`, and `focus-ring-within` are declared once as CSS there, and prime-ui adds none of its own, with their states as nested selectors on attributes the element already carries. The list parts of `Select` and `Combobox` wear `popover-panel`, `listbox-option`, and `listbox-heading`, and the `Menu` family's Content parts wear `popover-panel` while its `Item`, `CheckboxItem`, `RadioItem`, and `SubTrigger` rows wear `listbox-option`. `ToastItem` and `NotifyItem` wear `toast-stack-item`. A trigger button inside an input frame wears `input-button`, `Tabs` wears `underline-tabs`, `underline-tab`, `file-tabs`, `file-tab`, and `file-tab-slot`, and the date pickers wear `date-field`, `date-segment`, `calendar-nav`, `calendar-weekday`, `calendar-day`, and `calendar-day-range`. Layout-only lists stay inline. A TS module that only holds a string of utilities gets no IntelliSense and hides CSS as code. A lookup table keyed by a prop value (`Icon/icon.ts` sizes, `Field/state.ts` icons) is logic and stays in TS.
- **One elevation per kind of surface.** Every floating `*.Content` panel (`Popover`, `Select`, `Combobox`, `DatePicker`, `DateRangePicker`, and the `Menu` family) wears `shadow-popover`, which each gets through the `popover-panel` class. `Dialog.Content` wears `shadow-dialog`, and a drag ghost wears `shadow-sm`. Never use a stock Tailwind shadow such as `shadow-md`, which ignores the theme's shadow colors.

`styles.css` is the stylesheet this package **ships** (`exports["./styles.css"]`), so a consumer's Tailwind scans the compiled components, which automatic content detection skips under `node_modules`. It imports the tokens and holds an `@source`, with no `@import "tailwindcss"`, so a consumer writes one import after `tailwindcss`, and `design.mjs` cannot read it as a `--theme` entry. `tailwind.css` is tooling only. It imports Tailwind and `styles.css`, so the components' classes resolve for prettier-plugin-tailwindcss, `design.mjs`, and the browser specs.

### Doc comments

Open each component `.svelte` with an `@component` block: one-sentence description, a link to the bits-ui component if headless-backed, and a minimal `bind:` example. No prop docs there. Put those as `/** */` JSDoc on each `Props` field, with `@default` where the default is not obvious from the destructuring.

**These comments are the docs site.** The docs loader (`docs/src/loaders/components.ts`) renders the `@component` block as the component page's intro and builds the props table from the `Props` interface JSDoc, so:

- Write the block as markdown. Fenced ` ```svelte ` blocks become code samples.
- Link to a sibling component as `[`Select.Trigger`](./SelectTrigger.svelte)` or `[`Field`](../Field/Field.svelte)`. The loader rewrites those to docs links, and they also work on editor hover.
- Name the interface `Props`. The loader only recognizes an `interface`, so a part with no own props still declares one (the `id` narrowing above gives it a member, which also keeps `@typescript-eslint/no-empty-object-type` quiet).
- A new root export in `index.ts` gets a collection entry automatically. The docs page under `docs/src/content/docs/packages/prime-ui/components/` is still yours to add.

## Tests

Specs sit in a `__tests__` folder beside the code they cover. A `*.svelte.spec.ts` runs in Vitest **browser mode** (`render` from `vitest-browser-svelte`, `userEvent` from `vitest/browser`, and portaled content like `Select` is queried on `document`). A plain `*.spec.ts` runs in Node. Spec files run serially (`fileParallelism: false` in `vite.config.ts`): they share one browser page, and parallel files fight over focus so `userEvent.keyboard` types into the wrong input. `vite.config.ts` uses the plain `@sveltejs/vite-plugin-svelte` plugin, and the package has no app framework.

A spec earns each case by failing when the behavior breaks, so the suite holds no case that restates a class list, counts exports, or re-tests the browser (a native number input stepping on ArrowUp). The conventions that keep it that way:

- **Styles are asserted as computed style, never as a class name.** `test/computed-style.ts` loads the Tailwind theme into the shared page and resolves a utility to the color it paints (`colorOf`), beside `borderColor`, `backgroundColor`, and `textColor` readers. A spec that reads any computed style imports it, or the bare `test/tailwind.css`, so the theme is present even when the file runs alone. The one class-list check is the focus treatment, since focus-visible cannot be driven reliably from a test. A spec asserts the class that carries the ring: `focus-ring` or `focus-ring-within`, or a class that includes one, such as `input`, `date-field`, or `input-button`. `Input.Group`'s spec reads the group's computed `outlineWidth` instead, since a focused text input does match `:focus-visible`.
- **One rule over many inputs is an `it.each` table.** States, sizes, orientations, and the accept-or-veto pair of the controlled mode each read as one case table.
- **The `Field` cascade is tested once, in `Field/__tests__/Field.svelte.spec.ts`,** through `InputField.svelte` and `TextareaField.svelte` (in `Field/__tests__/fixtures/`) for the native inputs and `WidgetFields.svelte` for the widgets. A widget's own spec passes `state` directly and asserts its visual treatment. No per-widget `Error<X>` fixture.
- **For each value control, cover both binding modes with fixtures under `__tests__/fixtures/` beside the spec:** `Bound<X>.svelte` (two-way `bind:`, taking the props a case needs such as `disabled`, `state`, or `name`), `Controlled<X>.svelte` (function binding with an `accept` prop toggling veto vs accept), and `Undefined<X>.svelte` (the owner's state starts `undefined`, which must not throw). A fixture that forwards a `state` prop destructures it as `state: fieldState`, since a local named `state` collides with the `$state` rune.
- **A `Select` or `Combobox` spec closes the list in `afterEach`** (Escape when a `role="listbox"` is in the document), and a `Menu` spec does the same for `role="menu"`. A select unmounted while open leaves bits-ui reading destroyed deriveds and prints `derived_inert` warnings through the rest of the run.
